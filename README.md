# Car recommendation

> 可信购车榜单引擎：口径闸门 / MCDA 稳健性检验 / 8 维打分统一榜 / 总候选池 / 多源交叉核验 / 证据分层 / 历史回测。
> 无模型调用，同一输入必得同一输出。当前版本 **v10.2.6**（维度证据门槛统一 + 车名归一化 + 证据缺口检测）。

## 这是什么
WorkBuddy 用户级 skill。核心是「车型排行榜全链路」：按需搜榜入池→取数→闸门→8 维打分→稳健性→三档→审查→报告，
外加 工信部备案抓取/上榜预测/第三方视频证据/被动安全配置核验/数据仓库回测；
**v9.7.40 起附跨能源形式选车适配比较器 + 实际续航物理估算**（燃油/油混/插混/增程/纯电同台比较，物理模型算真实续航）。**榜单链路全程无模型调用**，
同一输入必得同一输出。原多模型辩论引擎已于 2026-11 移除——为什么不用 LLM 直接排名，见 SKILL.md《为什么出榜流程不含 LLM/辩论》。

现行榜单口径（v7→v9.5）：**打分榜是唯一权威名次来源**——原先单独按 kWh/万元、电耗排的「事实榜」已取消，
降级为打分主榜里标注「参考·不计分」的事实列；所有排行/比较/推荐都从打分榜取名次。
候选池收敛为单一事实源 `master_pool.json`，支持按提问搜榜摄入、12 源交叉核验。
**v9 起维度评分从「只看硬件配置单」升级为「硬件 + 可核验体验/持有成本证据」**：智驾/操控/车机/三电四维
按第三方实测与多源口碑调整（`experience_facts.json`，证据分级加权、无证据不插补），
保值率作为持有成本补偿进 `value` 维（`residual_values.json`）。页面展示区块统一由 `board_view.py` 注册表管理。
详见下方 v7–v9.5 演进节。

## 代码结构（v10.0 模块化）

根目录 81 个平铺脚本收进六个模块，**根目录只留薄壳入口**（`python3 monthly.py` 等命令照旧可用，薄壳只转发）。

| 模块 | 职责 | 规模 | 可独立发布 |
|---|---|---|---|
| `modules/contracts/` | 数据契约层：trims 字段/校验、车名归一化（零依赖零 IO） | 2 | ✅ 契约库 |
| `modules/research/` | 取数与证据采集，**所有对外网络调用的唯一出口** | 25 个采集器 + researcher | ✅ 检索取数 skill |
| `modules/physics/` | 电动车实际续航物理模型（零依赖） | 1 | ✅ 续航估算 skill |
| `modules/envscore/` | 跨能源环境分引擎（`engine.js` 唯一事实源 + 页面生成） | 2 | ✅ 用车条件适配计算器 |
| `modules/engine/` | 打分口径 / 闸门 / 事实注入（纯计算） | 26 | 口径库 |
| `modules/board/` | 出榜编排与渲染 | 19 | 主流程 |
| `modules/regress/` | 回归测试与失败回测 | 7 + 4 js | 项目专属 |

- **依赖只能向下**：`contracts` ← `research`/`physics` ← `envscore` ← `engine` ← `board`。反向 import 由 `layout_regress.py` 拦截。
- **数据落盘**：判据只有「能不能重建」——
  可重建的生成物放 `data/gen/`（不打包，用 `bootstrap_data.py` 生成）；
  人工采集核验的气囊/物理参数/基线池放 `categories/`（不可重建，必须随包）。
  读写一律走 `paths.cat()` / `paths.gen()`，不再手拼 `categories` 路径。
- **回归**：`layout_regress.py` 守结构、`bug_regression.py` 守口径，另有 4 个专项回归（回归脚本开发者自用，不随包发布）。
- **数据回流（出榜链路内置）**：`pipeline` / `board_v2` 出榜前自动把 `trims.json` 里已核验的官方指导价
  回流到候选池缺失的 `price_guide`，并在报告开头披露「回填了哪些、哪些是真缺口」；
  回填后仍存在「trims 有价而候选池无价」会被硬门禁拦下（防 canon 漂移）。
  手动批量维护仍可用 `master_pool.py --sync-prices --apply`。
- **碰撞成绩回流（同模式）**：`note` 里写了 C-NCAP/C-IASI 成绩但 `crash`/`safety_basis` 是空的车，
  出榜前由 `facts_sync.backfill_crash_from_text()` 自动解析进字段（`crash_systems.parse_score` 是唯一解析器，
  排除「未测」「无成绩」「第三方称但无得分率」「快充百分比」等假信号）。
  主榜新增「碰撞成绩」列：有成绩显示 `C-NCAP 90.7%`，已抽车未出成绩显示「在测」，无成绩显示「—」。
- **成绩 → 分数自动映射**：`official_safety_scores.json` 每个体系新增机器可读的 `map_spec`
  （C-NCAP 用得分率公式 `7.0+(pct-80)×0.155` 封顶 9.3、2021 及更早降 0.2；C-IASI/IIHS 按等级；
  NCAP 星级无乘员分项取保守档 8.3）。表**外**有成绩的车由 `safety_check.apply_auto_scores()`
  自动算分并写进 `scores.safety`，表**内**人工分绝不覆盖；报告披露「哪些车调了多少」。
  这样「有实锤」才真正影响排名，不再停留在标签上。`--no-auto-safety` 可做 A/B 对照。
- **映射表口径统一（v10.1.5）**：`car_scores` 里的分数必须能被 `map_spec` 复算出来，
  手填与公式不符会被出榜门禁拦下（`formula_mismatch`）。
  维护命令：`python3 safety_check.py --check-table` 体检、`--recompute --apply` 统一重算；
  候选池的 `scores.safety` 由 `sync_table_scores_to_pool()` 在出榜前自动对齐表分，
  不再出现「表里 8.7、榜上 8.9」两套数。
- **配置下拉二选一（v10.1.6）**：主榜每款车要么有配置下拉框，要么显式标注「配置待补」
  （`render_board_html.trim_selector()` 统一渲染，三处调用点收敛为一份实现）。
  没采到阶梯时不再静默——此前大众 ID.AURA T6 因汽车之家查无车系而没有下拉框，
  页面上看不出是"没有差异"还是"没采到"。回归 `t074` 逐行核对：有阶梯必须有下拉、无阶梯必须标待补。
- **数据分类修正（v10.1.8，用「删光缓存再重建」验证出来的）**：
  按「一条命令能否无损重建」重新划线，不再按体积。
  · 可重建（不打包）：`cell_facts` / `ice_crash` / `trims`（seed 用随包 manual，联网可补全）
  · 必须随包：`master_pool`（实测 `--intake` 重建出 291 车 / **0 车有分数**＝空骨架）、
    `trims_manual`（人工核验条目，联网也抓不回来）、`fact_library`（需 car_all 源库）、
    `universe_*`（盘点产物）、`airbags` / `vehicle_physics` / `baseline_car_ev`
  · 人工条目从 `trims.json` 分离到 `categories/trims_manual.json`，`auto_trims --seed-only`
    先用它生成基础库，再联网叠加自动条目——新装包不会再丢人工核验的配置表。
- **维度证据门槛统一（v10.2.5）**：`engine/evidence_gate.py` 用一张 `DIM_POLICY` 策略表取代多次特判——
  safety（碰撞成绩）、adas/cabin/control（实测/车主样本）、**quality（PPH 样本 ≥30）** 无证据则封顶；
  **space/value/powertrain 明确不封顶**（轴距、配置价格比、三电参数都是硬数据，封顶反而是用"没实测"惩罚硬指标）。
  加维度只需加一行，不用再写特判函数。quality 封顶用**中位**而非最低：有样本车分数低是问题被暴露，不是合格线。
- **证据补采（v10.2.5）**：`research/fill_experience.py`（`fill_pph()` 可库调用）用 `score_series` 批量补
  PPH/样本量，缺 `series_id` 时自动走"索引 → 站点检索"。本轮把 PPH 可用车从 4 款补到 10 款，
  quality 被封顶的车从 11 款降到 8 款。
- **车名归一化 + 证据缺口检测（v10.2.6）**：跨库比对车名一律走 `contracts/model_names.canon`
  （库写「特斯拉Model Y」、池写「特斯拉 Model Y」不再失联，否则它那份麋鹿 80.9km/h 实测被当成零证据）。
  `cross_verify.check_experience_gaps()` 出榜前扫描 note 里可核查的实测（麋鹿 XX km/h / 城市NOA 实车）
  但证据库缺记录的情况并披露——此前大众 ID.AURA T6 的麋鹿 80.02km/h 写在试驾稿里却没入库，
  被判「零实测」压到 7.8，而实测 75.2km/h 的车反而 8.5。补录 control/adas 两条证据后恢复 8.55/8.59。
  回归 `t080/t081` 同步升级：锚点改为**中位而非最低**、`min_proven=3` 小样本不封顶、quality 无样本
  force 到中位（填低填高同尺度）、canon 归一空格——堵死「没测过只能垫底」和"填低吃暗亏"。
- **体验维度举证封顶（v10.2.4）**：智驾 / 车机 / 操控这三类「纸面参数看不出来」的维度，
  无独立实测或车主样本的车，`scores` 封顶至「有实测车该维度最低分」（`experience_score.cap_unproven()`）。
  厂商宣传（`vendor_claim`）不算依据。**空间不封顶**——轴距/车长是硬数据，可纸面判定。
  同时撤销 11 款无 `adjust_reason` 的总分加减（含 MONA -4），并加门禁：`adjust` 非 0 必须写依据。
- **安全分换算单一入口（v10.2.3）**：`contracts/safety_score.py` 是「得分率/等级/星级 → 0-10 分」
  的唯一实现（cap 9.3）。此前 `engine/safety_check` 与 `research/sync_cncap` 各写一套
  （cap 10.0/floor 6.0），95%+ 高分段会给出不同分；research 不能反向依赖 engine，故下沉到契约层。
- **安全分举证封顶（v10.2.2）**：无官方碰撞成绩的车，`safety` 不得超过「有实锤车里的最低分」
  （`safety_check.evidence_cap()` 出榜前自动执行）。「没测过」不等于不安全，但不能被推断成
  「比测过的更安全」——这是举证责任，不是判劣。全池无实锤时不封顶（没有可校准的锚）。
  门禁从「无成绩车**中位**」收紧为「无实锤车**最高** ≤ 有实锤车最低」，并改为读 `crash` 字段，
  不再只比对映射表里那几款（此前本池一款都不在表里，检查被整体跳过）。
- **联网取数只走 research（v10.2.0，代码强制）**：除 `modules/research/` 外任何模块不得直接
  `import requests/urllib/httpx`，由 `layout_regress.check_network_egress()` 拦截（现状零越界，越界即 FAIL）；
  新增数据源必须注册进 `research/trim_sources.SOURCES`，存在性核对只出证据不出配置。
  **本条不接受任何例外**：极轻量联网也在 research 内实现一个函数供业务模块调用；
  `EXCEPTIONS` 对网络出口不适用（塞豁免也照样拦，回归 t077 验证）。
- **多源调度层（v10.1.9）**：`trim_sources.collect_trims()` 按「本地索引 → 站点检索 → 内容页存在性核对」
  顺序尝试，每步留痕（`attempts`），待补清单里能看出「试过哪些源、各因何失败」。
  前两个源能出结构化配置；第三个只确认「车确实在售 + 指导价区间」，**不产出配置**（防编造）。
  实测：易车 API 返回反爬 HTML、懂车帝 config 页 0 字节、有驾内嵌数据只有 1 条主推款，
  靠 requests 拿不到齐全的跨站配置表——要做得上浏览器自动化，故暂列为未接入。
- **打包体积预警（v10.1.9）**：解压后超过 3MB 上限的 92% 即告警，避免下次加随包数据时突然超限。
- **车系检索兜底（v10.1.7）**：`auto_trims.find_sid()` 在本地 A-Z 索引未命中时，
  自动走站点检索找车系页（`autohome.com.cn/<id>`）再解析，而不是直接放弃。
  实测：大众 ID.AURA T6、小鹏 MONA L05 两款「索引里没有、车系页其实存在」的车
  都被自动补出 4 款配置。回归 `t075` 锁死「有兜底、能提 sid、失败不猜」。
- 详细契约见 `MODULES.md` 与各包 `__init__.py`。

## 依赖（别人怎么装）
Python 3.10+。依赖没有打包进 zip，是标准的 Python 包管理方式：

    pip install -r requirements.txt          # 必需：requests、olefile

可选功能各自由依赖开关，**缺了不阻断出榜**，只少对应步骤并在 run.log 写明：

    pip install akshare                      # 乘联会大盘校验（装不上加阿里云镜像）
    npm install -g opencli                   # 汽车之家级别/价格对齐（fetch_specs.py）

最小说明：只装 requests + olefile，`pipeline.py`（闸门→打分→三档→审查→报告）
和 `forecast.py`/`warehouse.py` 全部可用；akshare 只影响大盘快照，opencli 只影响对齐一步。

## 生成物重建（新装包首跑必看）

发布包不含 `data/gen/`（可重建的生成物），首跑先体检再生成：

```bash
python3 bootstrap_data.py --check     # 缺哪些、怎么建、要不要联网、指纹是否过期
python3 bootstrap_data.py --apply     # 自动重建缺失项（每项一个命令，失败逐条报告）
python3 bootstrap_data.py --apply --all --force   # 版本升级后全部重算
```

6 个可重建生成物：`trims.json`（逐配置阶梯）、`master_pool.json`（总池）、`ice_crash.json`（碰撞）、
`cell_facts.json`（电芯）、`universe_car_midsedan_allprice.json`、`fact_library.json`；
后两个需前置输入（先跑 discover / 需 car_all 原始库），`--check` 会写明。

3 个人工事实库随包：`airbags.json`、`vehicle_physics.json`、`baseline_car_ev.json`——这些无法用代码重建。

## 被动安全配置为什么不进主分（v5.8）
侧气囊、头部气帘、前排中央（远端）气囊确实重要（NHTSA：侧气帘＋躯干气囊让近侧碰撞死亡率降约 30%）；
但 C-NCAP 2024 版乘员保护已含侧碰、柱碰、侧面远端乘员保护 8 分、保压气帘 3 分——
**气囊是拿分手段，得分率是结果**，再按配置加分等于重复计入。所以本项目：

- 报告出「气囊 侧/帘/中」**事实列**，不计入加权；
- 只对**无官方碰撞成绩**的车给 `scores.safety` 一个受限增量（|Δ| ≤ 0.3，标 low confidence，逐条可撤销）；
- 有成绩的车一律不叠加；「N 气囊」营销口径不映射到布尔字段；
- 未核验的写 `null`，不判劣、不造差异，`airbags.py --todo` 列待补清单。

详见 SKILL.md《被动安全气囊：事实列与受限修正（v5.8 · 方案 A）》及 `airbags.json` 里的 A1–A7 规则。

## 细分维度为什么不进主分（v5.9）

有人提过把轮胎品牌、制动距离、维修经济性、售后态度、保养经济性、底盘用料、试驾感受、
麋鹿成绩、防爆胎、电耗、空间、NVH、智驾、主动安全、流畅度、马力等十几项做成
「成绩好就加一点分，没数据或不确定不加分」。**本项目不做**，理由不是保守，是五个具体失效模式：

1. **缺数据不是随机的（MNAR）**：高曝光、营销预算足的车型披露的参数与实测远多于冷门车型，
   「有数据就加分」实际在给曝光度打分。
2. **选择性披露**：厂商只公布最优条件下好看的数字，缺的往往是不好看的；只加不减会系统性奖励会宣传的品牌。
3. **双重计数**：马力/电耗已在 `powertrain`，空间在 `space`，智驾/主动安全在 `adas+safety`，
   流畅度在 `cabin`，制动/麋鹿在 `control`——再加一次是同一份表现付两次分。
4. **稀疏噪声劫持权重**：覆盖率 10–30% 的维度，方差几乎全由「有没有数据」决定；
   十几个这样的维度叠加，MCDA 会被"谁被报道得多"主导。
5. **不可归一化**：100-0 制动跨媒体的胎温/载重/路面/初速不同；麋鹿只有少数媒体测；
   试驾、售后、NVH、流畅度是主观或口碑口径，样本小且立场不同。

替代方案写成了可执行的 `spec_facts.py` + `categories/spec_facts.json`：

- **16 项决策表**，分六类处置：已吸收·不加分（6）、封顶通道·双向（2）、仅事实列（4）、
  用户偏好滑杆（1）、不采集（2）、有官方口径·待准入（1，中保研 C-IASI 维修经济性指数）。
- **维度级准入门槛 G1–G4**：官方标准化口径 + 覆盖率 ≥70% + 可核验来源 + 加减双向对称。
  不达标就**整条维度禁用**，而不是把缺失记 0 分。本期 3 个待准入维度覆盖率都是 0%，全部禁用。
- **红线 `SCORING_ENABLED=False`**：`apply()` 只写 `c['spec_facts']`，并在返回前对
  `scores/total/adjust` 做前后深比较断言——事实库在代码层面不可能改排名。
- 官网/逐项参数配置照收（按 trim、带 url + quote + 日期），只进事实列与待补清单。

主观项（NVH、试驾）不做成默认权重，交给读者用 `--sliders` 自己拉。

## 具体配置推荐：为什么列、为什么不加分（v6.0）

榜单只按一个「带内推荐配置」打分，容易掩盖买车时真正要做的选择：
**同一车系不同配置的电池容量、电芯供应商、电压平台可能完全不同。**
例如 MG 07 的 610/650 版是苏州清陶 67kWh 半固态 + 400V/3C，
845 版是宁德时代 91kWh 三元锂 + 800V/5C；腾势 N8 加 1 万多 24.36kWh。

**结论：该列，而且这是很值得补的一层；但不该把它变成加分项。**

1. **层级错位**：榜单回答「买哪款车」，配置推荐回答「这款车买哪个版本」。写进加权分等于用配置性价比替代整车评价。
2. **配置性价比是场景函数**：同一笔 +1 万换大电池，有无家充、南方北方、通勤长途结论相反。
   腾势 N8 这一笔被一篇媒体称「六款中单位成本最划算」，另一篇明确写「只为续航加 1 万没必要」——
   没有唯一正确答案就不能进默认权重。
3. **MNAR 同样存在**：放出逐配置表的是高曝光车型，缺表就吃亏等于给披露完整度打分。
4. **「低配二线电池、高配宁德」的概括不成立**：零跑 C10 逐配置表写的是
   「国轩高科/亿纬动力/中创新航」**同配置多供应商混装**，选配置也规避不了；
   MG 07 是**技术路线分层**（半固态 vs 三元锂 + 400V vs 800V），不是供应商等级。
   电池包由整车厂集成，公开数据不足以按电芯品牌拆分长期可靠性——
   所以本项目**不给供应商排一线/二线/三线，也不映射任何分数**，
   只分类证据形状、只记「是谁、什么路线、上市多久」。

落成 `trims.py` + `categories/trims.json`：

- 按 trim 记录指导价 / 电池容量 / 电芯供应商 / CLTC / 补能 / 电机 / 上市时长，每条带 url + quote + 日期；
- 识别「加价-增配跃迁」：同年款内、每万元 ≥10kWh 或 ≥100km、目标须在价格带内；
  超过 1.5 万加价阈值判 `platform_step`（换整条三电路线），**只陈述事实与场景分支，不给单一建议配置**；
- 建议只从「评分配置」出发，其它支线的加价差异只进事实表；主观取舍按场景分支交还读者；
- 「评分配置」保持候选池原值，不替换、不改 `price_basis`、不动闸门；
- 带外车型（如腾势 N8，26.99–32.99 万）只作算法演示，绝不参与四榜名次。

**红线**：`SCORING_ENABLED=False`，`apply()` 只写 `c['trim_ladder']`，返回前对
`scores/total/adjust/price/trim` 做深比较断言。主报告出精简节，
逐配置表、带外示例与来源链接出 `out/trims.md`；`--no-trims` 可作回测对照。
本期 2026-10 首版核验 4/39 款；**v6.1 已补到 35/39**，见下节。

用户规则：**「排行榜如果没有价位段，就分几个价位段，每个价位段按前几排名，最后把这几个榜单汇总成总榜」**。

价值：保证每个价位段都有车进总榜，避免高端车凭产品力垄断前列。三种视图互补——
全价位主榜回答「综合产品力谁最强」、价位段子榜回答「我这个预算买哪款最好」、分段汇总总榜回答「各价位优等生凑一起」。

**事实榜融合核查（本次确认）**：现行产物无独立事实榜，kWh/万元、电耗已并入打分主榜作不计分参考列；
旧的全价位事实榜 HTML 是融合前历史中间产物，非现行口径。

**分段榜必须配三段评价**（`build_price_band_report.py`）：① 各段选车逻辑（入门选配置密度 / 主流选能力上限 /
高端选级别之外的服务与质感）；② 段内对比逻辑（同预算段比才公平，段内名次比总榜名次更有意义）；
③ 低价位段能否超越高价位段——用「剥离性价比后的 7 维归一化产品力分」实证：2026-10 中型纯电 SUV
入门段均值 80.1 > 主流段 79.4 > 高端段 79.0，全池产品力第 1 是 15.98 万 MONA L05（86.8）。
边界如实披露：高端段仅 1 款、主观质感项未纳入打分，产品力分只回答可量化维度，不等于「能买到且值得买」。
**铁律：全价位总榜与各段榜单都是 8 维全方面对比，性价比（11.7%）必须计入、不可剥离；
产品力口径绝不混进主榜、不改主榜名次。**

## v9.7.40 · 跨能源形式选车适配比较器 + 实际续航物理模型（2026-11-20，用户多轮需求）

用户从「12-14 万轿车里油车/油混/插混/增程/纯电放一起怎么比」出发，连续多轮确认，最终落地两件事：

### 1 跨能源形式选车适配比较器（`build_energy_compare.py` → `energy_compare.html`）
自包含单文件页面，离线可用。核心公式：
```
车型综合分 = 产品力主分（统一 8 维，75-90）+ 软调节（封顶±10）+ 硬条件惩罚（全额·降档·红标）
```
- **统一维度框架**：8 维能源中性，第 1 维「动力总成」对电车=三电、油车=三大件、混动=两者，共用 18% 权重，实现同台比较。
- **10 项用车条件**下拉（带人群默认值）：营运/冬季气温/年里程/单次最长里程/长途频率/充电/限牌/持有年限/高速占比/方盒子 + 驾驶风格/空调。
- **硬条件强处理**：无桩纯电 −15、极寒+低价纯电 −12、短持有纯电 −8、长途续航不足 −10、限牌油车 −8、营运油车 −10；触发即扣大分 + 降档 + 红标。换电车型（乐道L60/蔚来ES6等）在无桩/极寒/短持有/长途场景反而加分（据网搜共识：3分钟补能、电池恒温、车电分离保值）。
- **数据边界**：候选池 67 款仅纯电/插混有逐配置数据；燃油/油混/增程无数据入池，不编造车型；无电量数据的车不估算续航。

### 2 实际续航物理模型（`ev_range_model.py`，本能力单一事实源）
回答「某车实际能跑多少公里」——物理计算 + 真实数据给合理值，缺数据的车可估算：
```
场景电耗 = 基准电耗 × 工况倍率 × 温度(仅电池) × 空调 × 驾驶 × 胎压 × 轮胎 × 载重 × 热管理 × 电压
有效续航 = 电量 ÷ 场景电耗 × 100
```
- 基准电耗真实优先，缺失用物理回归 `4.48×车重(t)+5.88×Cd×迎风面积+0.61`（39 款拟合 MAE 0.69）。
- **修掉暖风双重计算**：温度只管电池活性（极寒1.20），暖风独立由空调季节基线负责——依据中国汽车报实测「-20℃无空调仅减10%」。
- **轮胎/胎压**：胎压每低0.1bar续航损失1-2%（已建模，默认原厂推荐不臆测）；低滚阻胎+5%但逐车数据缺失，默认中性不编造。
- 物理参数（整备质量62/风阻50/电压23/换电19，覆盖67款）采集自汽车之家参数页，存 `categories/vehicle_physics.json`。
- **真实数据校准**：内置懂车帝/汽车之家实测 11 条，模型达成率市区92.9%/高速55.7%/冬季52%，与实测均值偏差均 ≤5pp。
